SDD Design Skills · pipeline

From a fuzzy requirement to an experienceable screen——hand off forward, hand defects back.

Four skills hand off in sequence; each step produces exactly one .sdd/ document that is the sole input to the next. But the pipeline is not a one-way street: when a downstream skill finds a defect that belongs upstream, it routes the fix back to the owner and re-syncs forward — and every document has exactly one skill that may edit it.

Stage 01 · Explore

ux-spec

→ DESIGN-BRIEF.md
Owns: need · flow · AC scenarios

Reach 100% intent consensus in experience language, then pin the intent down with concrete scenarios (happy path / boundaries / exceptions). These scenarios are the acceptance criteria (AC) — the pipeline's single home for them.

Hands off to
▶ ui-spec
Absorbs handback
⤴ from ui-spec / design-build — “need·flow·AC wrong or infeasible”
Re-entry
amend: revise only affected scenarios → re-take Confirm/Go → flag downstream UI-SPEC / build/ stale
Stage 02 · UI Design

ui-spec

→ UI-SPEC.md
Owns: screens · elements · states · values

Turn the brief into every screen's elements, positions, hierarchy, states, and interactions, plus the concrete visual values resolved from the design guideline. No scenarios, no AC — it only references the brief for coverage.

Hands off to
▶ design-build
Hands back to
⤴ ux-spec (when a scenario is infeasible as an experience)
Absorbs handback
⤴ UI-structural defects from design-build
Re-entry
reconcile: revise only affected screens + re-run the coverage check

→ UL-MAP.md
Owns: shared vocabulary dictionary

Fed by downstream

Stage 04 · Build

design-build

→ build/ (HTML or Figma)
Owns: real screens + playable prototype

Build the screens from UI-SPEC and verify each one against the brief's AC as the oracle. No new design decisions — honor what the spec fixed; for open details, commit sensible values and list them as assumptions.

Decision rule
low-impact open detail → patch in place; structural / AC-affecting → hand back
Hands back to
⤴ ui-spec (screen/state/value) / ux-spec (infeasible scenario)
Re-entry
re-sync: rebuild only the affected screens in an existing build

Handback routing

The nature of the defect decides which owner it goes back to

The downstream skill never patches over the defect or cross-edits an upstream document; it emits a structured handback (what's wrong, where it traces to, the proposed fix) and routes it to the owner.

Nature of the defectRoutes back toDocument fixed
Need / flow / scenario (AC) wrong, missing, or infeasible as an experience ux-spec DESIGN-BRIEF.md
Screen / element / state / interaction / visual value missing, contradictory, or unbuildable ui-spec UI-SPEC.md
Vocabulary drift / a new term to capture ul-mapping UL-MAP.md

Two rules that keep it safe

So the loop converges instead of ping-ponging forever

Single ownership

Each document is edited by exactly one skill

brief→ux-spec, UI-SPEC→ui-spec, UL-MAP→ul-mapping, build→design-build. Feedback works through handback + re-sync, never cross-editing — which is exactly what lets “AC has one home” hold.

Convergence first

If it's a low-impact local fix, don't hand it back

design-build just commits sensible values for details the spec left open; only structural / AC-affecting defects escalate. Batch all handbacks into one pass to avoid back-and-forth ping-pong.

.sdd/ output structure — one folder per feature; cross-feature shared files live at the root.

.sdd/ ├── UL-MAP.md # cross-feature shared vocabulary (optional) ├── DESIGN-FOUNDATIONS.md # cross-feature design foundations (optional) └── {yyyy-MM-dd}-{feature-slug}/ ├── DESIGN-BRIEF.md # ux-spec: need + flow + AC scenarios ├── UI-SPEC.md # ui-spec: UI design + visual values └── build/ # design-build: single HTML file or Figma link
