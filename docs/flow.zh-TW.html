SDD Design Skills · pipeline

從模糊的需求，到可體驗的畫面——
往前交棒，缺陷就往回退件。

四個技能依序交棒，每一步只產出一份 .sdd/ 文件當作下一步唯一輸入。而 pipeline 不是單行道：下游發現缺陷屬於上游時，會退回擁有者修正、再往下重同步——每份文件永遠只有一個技能能編輯。

四階段 · 各司其職

每個技能做什麼、擁有哪份文件、與誰交換退件

點上方地圖的任一階段可跳到對應卡片。「擁有」標籤代表：這份文件只有它能編輯——回饋一律靠退件與重同步，而非越權改檔。

階段 01 · 探索

ux-spec

→ DESIGN-BRIEF.md
擁有：需求 · 流程 · AC 情境

用體驗語言達成 100% 意圖共識，再用具體情境（happy／邊界／例外）把意圖釘死。這些情境就是驗收條件（AC），全 pipeline 唯一的家。

交棒給
▶ ui-spec
吸收退件
⤴ 來自 ui-spec / design-build 的「需求·流程·AC 有誤或不可行」
再進入
amend：只改受影響情境 → 重取 Confirm/Go → 標記下游 UI-SPEC／build/ stale
階段 02 · UI 設計

ui-spec

→ UI-SPEC.md
擁有：畫面 · 元件 · 狀態 · 視覺值

把 brief 變成每個畫面的元件、位置、階層、狀態、互動，以及依 design guideline 落定的視覺數值。完全沒有 scenario／AC——只引用 brief 做覆蓋確認。

交棒給
▶ design-build
退件給
⤴ ux-spec（情境作為體驗不可行時）
吸收退件
⤴ design-build 的 UI 結構缺陷
再進入
reconcile：只增量修訂受影響畫面 + 重跑覆蓋檢查
階段 03 · 語彙（選用）

ul-mapping

→ UL-MAP.md
擁有：共用語彙字典

讓「使用者用語 ↔ 元件名 ↔ UI 標籤 ↔ design token」指向同一概念。建議在 ui-spec 之後執行，把設計實際落地的語彙收攏起來。

由下游餵入
▶ ui-spec／design-build 的 new-terms list → UPDATE 收攏
退件給
⤴ ux-spec（需求歧義）／ ui-spec（命名不一致）
階段 04 · 實作

design-build

→ build/（HTML 或 Figma）
擁有：成品畫面 + 可播放流程

照 UI-SPEC 把畫面做出來，以 brief 的 AC 為 oracle 逐條驗收。不重做設計決策——spec 定的照做，留白處補合理值並標為假設。

決策規則
低影響留白 → 就地補值；結構性／影響 AC → 退件
退件給
⤴ ui-spec（畫面/狀態/值）／ ux-spec（情境不可行）
再進入
re-sync：既有 build 只重建受影響畫面

退件路由

缺陷的本質，決定它退回哪個擁有者

下游不自行硬補、也不越權改上游文件；它產出一個結構化退件（缺陷是什麼、對應哪份文件的哪處、建議怎麼改），路由給擁有者。

缺陷本質退回哪個技能修哪份文件
需求／流程／情境(AC) 有誤、缺漏，或作為體驗根本不可行 ux-spec DESIGN-BRIEF.md
畫面／元件／狀態／互動／視覺值 缺漏、矛盾，或做不出來 ui-spec UI-SPEC.md
語彙漂移／新出現的名詞要收攏 ul-mapping UL-MAP.md

兩條保命規則

讓閉環收斂，而不是無限來回

擁有權唯一

每份文件只有一個技能能編輯

brief→ux-spec、UI-SPEC→ui-spec、UL-MAP→ul-mapping、build→design-build。回饋靠「退件＋重同步」達成，不靠越權改檔——這正是「AC 只有一個家」得以成立的原因。

收斂優先

能就地低影響解決的，就別退件

design-build 對 spec 留白的細節補合理值即可；只有結構性／影響 AC 的缺陷才升級。退件要批次一次給完，避免一來一回的 ping-pong。

.sdd/ 產出結構 — 一個功能一個資料夾，跨功能共用檔放在根目錄。

.sdd/ ├── UL-MAP.md # 跨功能共用語彙（選用） ├── DESIGN-FOUNDATIONS.md # 跨功能設計基礎（選用） └── {yyyy-MM-dd}-{feature-slug}/ ├── DESIGN-BRIEF.md # ux-spec：需求 + 流程 + AC 情境 ├── UI-SPEC.md # ui-spec：UI 設計 + 視覺數值 └── build/ # design-build：HTML 單檔 或 Figma 連結
